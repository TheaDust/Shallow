# 实现持久化应用状态

## 工作流

1. 从当前需求提取对象、稳定 ID、父作用域、角色、允许的状态迁移和持久化边界；不得根据题目名称预设领域模型。
2. 指定唯一权威状态。列表、详情、计数、搜索、活动记录和刷新都从它派生，不维护互相漂移的镜像真值。
3. 把一次用户动作实现为 UI 意图、服务端校验、原子写入、可观察响应的完整闭环。写入失败时保留最近一次成功状态。
4. 在服务端可信边界重新检查身份、权限、当前版本与前置条件；前端隐藏或禁用控件只是同一规则的呈现。
5. 为稳定 ID、状态机、权限矩阵和事务失败编写纯逻辑或后端测试；为入口名称、容器范围、成功状态及错误反馈编写组件测试。
6. 最后执行重载检查：刷新或重启后，成功操作仍存在，失败操作没有留下部分数据。

## 建模约束

- 使用不可变 ID 建立引用；显示名称、排序位置和连续编号不得冒充身份。
- 编号若有作用域，只能在需求明确的父对象内分配；事务失败不得消耗编号，除非需求明确相反。
- 状态迁移使用显式动作和允许边，不接受客户端直接提交任意最终状态。
- 创建、编辑、删除、关联、授权等多记录操作必须全部成功或全部失败。
- 派生计数、时间线、搜索结果和可操作性应在一次成功写入后保持一致。
- 具有版本历史的对象用不可变快照与显式父边建模；历史、当前指针、比较结果和内容读取来自同一关系图。
- 带审批或检查门槛的终态操作在原子提交前重新计算全部门槛，不能复用页面加载时的旧判断。
- 每个请求重新鉴权，不信任客户端传入的角色、所有者或 `canEdit` 一类标志。
- 并发写入至少检测陈旧版本，选择拒绝、重试或合并之一，并向用户提供明确结果。

## 跨层实现顺序

1. 先实现类型、校验和纯状态迁移。
2. 再实现存储事务及 API 合同，包括成功、校验失败、无权限、冲突和不存在。
3. 最后连接 UI；提交中防止重复动作，成功后使用服务端权威结果更新，失败后恢复可操作状态。
4. 多个页面消费同一对象时，验证从任一入口修改后，其他入口刷新可观察到同一结果。

不要针对需求示例中的名称、用户、编号或内容编写特例。预置技能只提供方法；具体对象、字段、动作、权限和初始关系必须由当前需求与当前项目决定，并由本次模型调用实际实现。
