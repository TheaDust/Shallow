# 行动：实现当前工作包

本工作包包含一个完整模块或相互依赖的需求组。在同一次调用内按以下顺序工作：先规划，再实施。规划与实现都必须严格符合需求文档：不缩减、不变更、不推迟需求描述的行为。

1. 规划（先写计划，再写代码）。通读本包全部需求原文、验收场景与引号原词，按上下文区分控件文案、数据值与示例；检查现有项目结构、相关代码与 ARCHITECTURE.md（如存在）。然后用简短条目写出实施计划：
   - 每条需求 ID 对应的界面、接口与数据改动，以及对应的检查方式；
   - 场景的初始状态、逐字入口/字段/反馈文案、相关图片中的交互结构，以及操作后应变化的状态；
   - 复用的既有接口与约定，需要新建或调整的公共能力与状态归属；
   - 端到端实施顺序与关键用户路径。
   计划必须覆盖本包每条需求和场景新增的具体约束；重复或抽象指代同一流程的场景可合并核对，不重复设计动作或把占位语当作 UI 文案。发现需求与既有实现的冲突时在计划中写明处理。计划足以指导本包实现后立即继续，不等待确认。
2. 实施。按计划统一实现数据模型、接口和界面，贯通完整业务链路：用户操作、界面状态、网络请求、服务端校验、状态变更、持久化与重新读取后的呈现。实现需求明确要求的输入校验、状态及持久化；不要为某个示例数据或测试定位器实现特例。保持接口清晰、命名一致，复杂或边界逻辑拆分为可独立测试的单元。
3. 检查。按自测约定执行：至少完成与改动相关的构建或类型检查；复杂或边界逻辑编写传统测试并用 `run_tests` 运行；仅当这些检查无法回答真实浏览器行为问题时，才用昂贵的 browser 工具验证关键路径。
4. 交接。逐条核对本包需求 ID 的实现情况；把影响后续开发的稳定约定同步到 ARCHITECTURE.md——下一个工作包由没有本会话记忆的新会话继续开发。将尚未解决的问题写进简短回执。
