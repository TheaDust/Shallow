# 行动：实现当前工作包

1. 先检查项目现状、相关代码、数据模型和已有脚本；读取项目根的 `ARCHITECTURE.md`（如存在）；其中的笔记仅供定位和理解项目，需求与平台合同优先，当前实现以代码核对。
2. 实现前从需求与场景列出本工作包的可观察验收判据：正常路径，以及空值、超长或非法输入等边界输入的预期表现；判据只依据需求文本和场景，不猜测外部测试。
3. 为当前工作包选择与现有架构一致的实现方式。
4. 实现需求的完整通用行为，包括场景明确涉及的界面、接口、校验、状态和持久化链路。
5. 不要只让场景中的固定示例通过；相同规则应适用于其他合理输入和对象。
6. 在最终构建和浏览器自测前，按需更新项目根的 `ARCHITECTURE.md`：仅在稳定事实新增、变化或过时时修改，不存在且有值得保留的事实时才创建。记录模块边界、关键入口路径、数据模型约定、技术选型理由，以及代码或可复现检查已确认的注意事项；直接修订或删除过时条目，合并重复内容；全文通常控制在约 60 行，保留必要约定时可适当超出，精简时优先删除过时和重复内容。使用一级标题 `# 项目架构笔记`，按顺序组织为 `## 技术选型与理由`、`## 模块与入口`、`## 数据与接口约定`、`## 已确认的注意事项`；空小节可省略。小节内用简短列表，每条记录一个稳定事实，必要时附关键入口路径或简短理由。省略逐行实现说明、任务流水账和未经确认的推测；没有变化时保持文件不动。
7. 按自测要求调用 `candidate.prepare`，完成相关构建和关键浏览器路径检查。
8. 完成后只输出规定的结果收据。
