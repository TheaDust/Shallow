【可访问 Web 交互契约】
黑盒浏览器通过可见文本、角色、可访问名和用户操作检查行为。需求明确指定的角色、名称、数量、容器归属及状态属性必须逐字实现；未指定时按控件语义选择原生元素，不把单个场景的 DOM 结构推广到所有页面。

输入控件使用符合用途的原生类型，包括文本、密码、多行文本、搜索、复选框、单选框和选择框。需求给出 label 时将它关联到控件；给出 placeholder 时实现该 placeholder，不能用容器名称代替输入控件名称。需求只给出 placeholder 时仍让控件可访问，不凭空要求额外的可见 label。需要显示指定校验错误时在页面渲染该错误，不只依赖浏览器原生校验气泡。

操作使用可访问的 button；有页面导航语义的入口使用带 href 的 link。若需求明确允许多种角色，选择与现有产品一致的一种；若指定角色则严格遵守。对象列表可用 article、li 等有语义的容器承载条目；打开对象的方式依需求可为条目本身、其中的 button 或 link。条目及其操作应能按对象名称或所属容器区分，不嵌套交互元素。需求要求 heading 时使用真实 <h1>–<h6>，一般标题也保持合理的文档层级。

菜单按需求实现：要求 menu/menuitem 时提供相应角色与键盘行为；要求菜单内 button 时保留 button。图标按钮可用稳定的 aria-label，无需额外显示文字；可见文字或 aria-label 与需求给出的动作名称一致。不同条目的同名操作可以重复，通过 article、row、dialog 等容器限定；同一作用域内应能明确定位目标操作。次要操作是否悬停后出现，依据需求和参考图决定，并保证键盘聚焦时也能操作。

表格数据按需求使用 table、row、cell；普通卡片或搜索结果无需强行改成表格。下拉、单选、多选分别使用可访问的 option、radio、checkbox。不可用状态用原生 disabled；展开、按下、选中等状态在需求涉及或控件语义需要时更新相应 ARIA 状态。若需求要求切换后改变动作名称，名称与状态同步变化。

对话框有可访问名称，需求指定标题或角色时逐字对应；打开时背景不可操作，关闭后恢复合理的焦点位置。成功或错误反馈按需求显示可见文字，适合通知的反馈使用 status 或 alert；反馈中的操作是真正可操作的控件。表单或搜索容器需要名称时，避免其可访问名与内部输入控件的名称冲突，确保 label 定位落在可输入的控件上。

创建、编辑、删除、过滤或切换后，检查目标对象和状态的实际变化；刷新或重新进入后的结果与持久化要求一致。需求明确规定视觉呈现或 DOM 属性时，也要实现这些细节，不能只显示成功提示代替结果。
