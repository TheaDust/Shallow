# Builder 需求预检：调用已有 Planner 测试并获得反馈

日期：2026-09-21  
状态：设计提案，尚未实现；本文用于后续实现与评审。  
代码核对基线：`3eff56a`。

## 1. 建议与目标

增加 `check_requirements` 工具：Builder 在当前工作包实现过程中，请求控制器执行已生成的 Planner 探针，获得经过过滤的结果，在同一会话中及时修复。完整探针计划、执行脚本和 Planner 推理仍由 Judge 持有。

目标是提前发现需求遗漏、缩短反馈延迟、减少模块边界重新理解代码的成本。预检通过表示当前候选通过了本次执行的探针；正式功能状态仍由控制器的模块边界及最终验收决定。

建议先补齐失败归因与探针纠错，再开放工具。错误测试的反馈越及时，也可能越早误导实现，因此两部分应一起设计和验证。

第一版覆盖主线的 `implement` 工作包，包括该包的同会话续接。范围由控制器绑定。Baseline、模块修复和交付修复暂不接入，后续有实际需要时再确定各自的范围与预算归属。

## 2. 当前基础与缺口

当前控制器在 Builder 执行期间并行生成原子需求的探针并缓存。工作包返回后检查安装、构建、启动及候选一致性；模块边界执行业务验收并按现有配额修复。

| 现有组件 | 已有能力 | 本功能需要补充的部分 |
| --- | --- | --- |
| `PlanCache` / `spawnPlanGeneration` | 按验收包保存和读取计划，读取时校验 | 显式区分生成中、可用、生成失败，以及纠错后的计划版本 |
| `auditPacket` | 定位恢复、失败复现、执行故障分类 | 基于需求的语义复核；供开发预检复用且不发布正式状态的执行入口 |
| `CandidateRuntime` | 候选构建、缓存、一致性检查、独立运行数据 | 与开发服务协调、贯穿预检的取消与资源回收 |
| `toBuilderShadowObservation` | 脱敏后的白名单失败观测 | 需求关联、归因结论、覆盖信息及有限异议入口 |
| Pi Worker IPC / `BuilderApp` | 父进程持有开发服务，工具通过 IPC 调用 | 仅当前工作包有效的预检能力与请求生命周期 |

已有 schema 校验能拦截非法操作、部分无依据路径、缺少断言等问题；定位精化只能修改定位器；新应用实例复现能排除部分偶发失败。这些机制不能证明测试在业务语义上符合需求。

## 3. 工具与验收的分工

| 能力 | 主要问题 | 对功能状态的影响 |
| --- | --- | --- |
| `run_tests` | 本地逻辑、状态、边界与组件行为是否正确？ | 开发诊断 |
| `browser` | 页面实际是什么样，交互为何失败，视觉和可访问结构是否合理？ | 开发诊断 |
| `check_requirements` | 独立生成的需求探针在当前候选上发现了什么？ | 开发诊断，不直接写入 `verified` |
| 模块边界验收 | 当前模块的组合行为是否成立，修复是否破坏本模块已通过的路径？ | 控制器决定正式状态及修复的保留或回滚 |
| 最终全量验收与交付验证 | 最终版本的功能及运行合同是否成立？ | 发布最终结果，沿用现有交付规则 |

保留 `browser`。Builder 用它解释预检失败、观察页面、验证参考图或探针未覆盖的交互，不需要再手写一套与 Planner 探针相同的流程。

第一版保留模块边界验收范围和现有至多两轮修复配额。后续工作包可能改变先前通过的行为；预检结果也不能替代模块组合检查。正式验收使用当前候选重新执行，不直接采纳开发期缓存的 pass。

隐藏计划仍然允许 Builder 从反馈中学习。因此，边界复跑同一计划属于确认与回归，不能视作从未参与开发的全新测量。测试独立生成、执行过程由控制器持有、裁决权独立于 Builder，这些边界仍然保留。

## 4. 调用流程

```text
Builder 实现当前工作包
    → run_tests / 构建等常规检查
    → check_requirements
        → 核对范围、计划状态、调用额度和剩余时间
        → 停止开发服务并释放开发浏览器
        → 准备候选，使用独立初始数据执行缓存探针
        → 对失败做定位恢复、语义复核及必要复现
        → 关闭候选服务与浏览器，返回过滤后的反馈
    → Builder 在当前会话修复，必要时 browser 调试
    → 有额度时复查一次
    → Builder 返回完成回执
    → 控制器执行既有可运行检查点与模块边界验收流程
```

建议提示 Builder 在本包实现完成后预检一次，修复后最多复查一次。没有可用计划或预算时继续开发、如实交接；工具未执行不能被解释为需求失败。

### 4.1 请求与范围

建议使用一个工具、两个动作。以下是拟定契约，不是现有 API。

```json
{ "action": "run" }
```

`run` 不接受脚本、任意测试路径、期望值、候选目录或可自选的 case 列表。控制器根据当前工作包确定相关原子验收包，检查其全部可执行的缓存 case，并报告未执行部分。Worker 无权改变这个范围。

计划尚在生成时返回 `not_ready`，生成失败时返回明确原因。工具不为普通查询重复发起 Planner 生成，也不等待整份计划直至占满 Builder 时限。异议处理中的有依据重建是单独受限的纠错路径。

不能仅因前置需求尚未 `verified` 就跳过测试：已实现的可运行前置功能仍可参与场景准备。同包内部依赖也允许执行。控制器明确知道外部前置尚未实现时，才说明该 case 的执行条件不足；运行中准备步骤失败还需要继续归因。

### 4.2 返回结果

返回本次检查 ID、候选版本标识、覆盖需求、已执行与未执行数量，以及各需求的反馈。建议每项反馈包括：需求 ID、诊断 ID、检查目的、实际观察、结果分类、与需求有关的简短说明，以及必要的可访问结构片段。

| 分类 | 含义 | Builder 的后续动作 |
| --- | --- | --- |
| `pass` | 当前候选通过本次已执行的探针 | 继续交接；不能称为正式 verified |
| `behavior_failure` | 有需求依据的行为检查失败，并完成必要复现 | 按需求修复实现 |
| `probe_issue` | 定位、准备步骤或预期存在探针问题，当前无法建立有效判词 | 阅读诊断；必要时提出有依据的异议 |
| `execution_error` | 浏览器、构建启动、候选一致性或运行资源导致检查未完成 | 根据具体故障处理，不能据此断言业务错误 |
| `not_ready` / `budget_exhausted` | 计划、已知前置条件或额度不允许继续 | 继续允许的开发工作，交接时说明未检查范围 |

部分执行应逐项返回结果和未执行原因；存在未执行项时不能把整个工作包汇总为全部通过。

返回通道沿用诊断脱敏及长度限制。可以提供需求中已有的预期和本次实际观察，但不返回完整 ProbePlan、可执行测试代码、全部步骤、Planner 原始输出或私有日志路径。当前原始 Playwright 错误可能带定位表达式，接入时需检查并过滤，不能只把整个异常字符串透传。

工具不更新 accepted SHA、不提交应用、不回滚代码、不消费模块边界修复配额。未修好的反馈由现有正式流程处理。

## 5. Planner 质量与失败归因

### 5.1 测试应关联需求依据

在 Judge 内部为 case 保存需求 ID、相关场景、预期结果的原文依据、初始状态、准备操作，以及定位约束的来源。区分需求明确要求的角色或容器与 Planner 自行选择的定位方式。

程序验证引用确实出现在对应输入中，继续执行现有 schema、覆盖和定位约束检查。原文引用存在仍不足以证明推导正确；不把这一校验描述成自动证明业务语义。

语义检查重点包括：

- 初始种子是否被误读为 GIVEN 所需的操作后状态。
- 登录、创建、归档等准备动作是否完整，并有需求或前置需求依据。
- 是否增加需求未规定的文案、角色、标题层级、限制或操作。
- 断言是否检查目标操作的结果，能否识别按钮无效果、数据未保存等情况。
- 用例是否依赖先前 case 留下的状态，或把异步内容暂未出现当作确定缺失。

### 5.2 两类纠错路径

**定位纠错**复用已有定位精化机制，保持操作、输入和预期不变。例：需求只要求打开同名对象，页面用 link，计划用了 button；有页面证据时可换成同一目标的合理定位。

**语义纠错**需要新增受限入口。例：需求写 active 种子，计划直接去归档区恢复；或者计划要求需求从未规定的反馈。复核确认具体冲突后，按原需求重建受影响 case。该入口与只改 locator 的精化保持区分。

语义复核输入限于原始需求、祖先及前置文字、种子数据、原计划和黑盒观测；Planner 不读取业务源码、diff 或 Builder 会话。可以使用不同调用上下文进行复核，但同一模型再判断一次并不保证正确，结论必须指出具体依据和冲突。

第一版在首次失败或有具体依据的异议时触发语义复核，不为每个成功 case 额外调用模型。无效计划不能通过删除困难 case、降低预期或缩减需求覆盖来获得通过；覆盖不足就报告未验证。

### 5.3 归因与处理

1. 先区分执行故障、定位问题和可观测的行为失败。
2. 在要求 Builder 修复前，检查失败 case 的需求依据与场景准备。稳定失败只证明可复现，不证明测试正确。
3. 确認是探针问题时，保留应用代码，修正探针并在同一候选上重新执行。
4. 需求依据明确、准备成立且失败在干净应用实例上复现后，才输出 `behavior_failure`。
5. 无法归因、纠错失败或预算不足时返回无法判断。正式验收映射为 `inconclusive`，不能因此把可运行应用判为业务失败或触发错误回滚。

同样的归因规则应进入模块边界验收。仅在开发工具中纠错、而正式验收仍执行已知无效计划，会重新制造误报。

### 5.4 Builder 异议

```json
{
  "action": "review",
  "checkId": "当前工作包已返回的检查 ID",
  "diagnosticId": "需要复核的诊断 ID",
  "requirementId": "关联需求 ID",
  "quote": "需求原文引用",
  "reason": "反馈与原文的具体冲突"
}
```

Builder 无需看到完整测试就能提出异议。控制器先验证 ID 归属和引用，再将必要内容作为待核对信息交给 Judge。Builder 的理由不能直接撤销判词，也不能指定替换后的预期；不提供提交任意测试代码的接口。

每个 case 在当前运行内最多一次语义修正，自动复核与主动异议共享该额度。重复请求返回已有结论，Worker 重启或同包续接不重置计数。复核发现问题但没有时间复验时，返回未验证；纠错本身不能算 pass。

## 6. 候选、资源与预算

### 6.1 执行隔离

预检通过父进程执行。请求期间暂停 Builder 的写文件和 shell 执行；关闭 Worker 的共享开发浏览器，停止 `BuilderApp` 持有的开发服务，再运行候选检查。工具需使用顺序执行模式，同时以候选摘要检查兜住后台进程或外部写入导致的变化。

候选仍通过 `CandidateRuntime` 准备。每次要求独立复现的应用运行使用新的数据目录和浏览器上下文，保留源码中的种子定义；不复用 Builder 自检产生的登录态和业务记录。所有权与清理责任留在父进程。

预检结束后释放 Judge 浏览器、服务及临时数据；向 Builder 说明开发服务已停止，需要继续 browser 调试时重新 `app start`。内存背压沿用已有候选构建和浏览器启动机制。

Worker 超时、中止、IPC 断开时，父进程必须取消正在进行的预检并等待资源回收，再进入后续流水线。单纯让 IPC Promise 超时不足以结束底层构建或浏览器。取消链路是实现验收项。

### 6.2 调用额度

建议每个实现工作包最多两轮实际预检：实现后一次，修复后一次。额度归控制器管理，在同包续接和超时新会话重试之间累计。相同候选与计划的缓存查询不增加轮次；计划尚未就绪的查询不发起测试。

一轮内部可能包含定位恢复、失败复现或一次获准的语义修正复验。这些动作共用该轮截止时间，不另获 Builder 时间；内部恢复次数沿用既有有界策略，并与语义修正额度分别记账。

预检、复核及异议处理全部消耗当前 Builder 调用和实现阶段的剩余时间。建议初始试验给每轮再设 5 分钟上限，实际取该上限、当前调用剩余和实现阶段剩余的最小值。5 分钟是待实测的起始值，不是已证明的最优配置。异议仅使用关联轮次尚未耗尽的额度，不能重新获得一整轮时间。

不得用预检重新开启实现计时器，也不能动用预留给后续阶段的时间。资源清理沿用明确的独立超时。工具返回次数和后台真实执行次数都要计量，避免低估成本。

### 6.3 缓存与证据有效性

预检结果至少关联候选输入摘要、构建证据、计划摘要和执行合同。复用前检查当前候选仍匹配；源文件、依赖、构建、种子合同或计划有相关变化时，旧结果不能继续用于当前版本。

只复用已完成且仍有效的检查结果。暂时的执行故障、计划生成中等状态不能被永久缓存成当前候选的结论。

探针纠错后保存新计划及其摘要，保留原计划、修改依据和关联结果的私有审计记录。该 case 的旧判词失效，正式验收需依据新计划重跑；不能把旧失败直接改为通过，也不能沿用旧计划下的 pass。

## 7. 实现职责与边界

| 位置 | 建议职责 |
| --- | --- |
| 主线 pipeline | 创建当前包预检上下文，绑定范围、额度、截止时间和日志；保持正式状态管理 |
| Builder 执行端口与 Worker client | 显式传递可用能力；父进程处理请求、取消和清理，不把函数或计划序列化到 Worker |
| Worker 自定义工具 | 校验工具参数、关闭开发浏览器、发 IPC 请求、返回过滤结果 |
| Judge 执行与复核 | 读取缓存计划、运行探针、归因与有限纠错；共用既有 Runner 和恢复规则 |
| CandidateRuntime / BuilderApp | 协调进程、端口、候选一致性与数据生命周期 |
| 诊断转换与事件 | 区分开发预检和正式验收，提供白名单反馈及私有审计记录 |

只在控制器提供当前包能力时注册工具，Baseline 等没有该能力的入口保持原行为。沿用现有 IPC 模式，实现专门的预检请求处理，不为此引入通用任务调度或插件框架。

不直接让工具调用包含发布状态和修复调度的整个模块边界流程。应复用计划校验、探针执行、恢复和观测转换，使预检与正式验收共用规则，并各自控制状态出口。

预检新事件通过现有 `state.record` 记录，补充类型和中文日志。至少记录包与调用 ID、候选和计划摘要、覆盖范围、轮次、各类耗时、实际执行次数、纠错原因及缓存命中。完整计划和 Planner 原始输出保留在 Judge 私有通道，不通过 Builder 回执或正式 ARC 通过事件发布。

## 8. 实施顺序与验证

### 第一步：失败归因与计划纠错

补充 case 依据、受限语义复核及计划失效规则，先通过可确定答案的本地样例验证。重点覆盖：合理 link 被误认为缺 button、active 种子被误读为已归档、遗漏准备动作、臆造预期、真实保存失败，以及 no-op 操作被宽松断言漏掉。

### 第二步：接入当前工作包工具

接通 IPC、候选执行、白名单结果和同会话反馈；验证：

- 工具无法越过当前包选测试、访问计划文件或修改正式状态。
- 计划生成中、失败、部分可执行和无预算都有明确结果。
- 首次反馈后可在同会话修改并复查；每包额度不能靠重启 Worker 绕过。
- 开发服务与 Judge 不争端口，运行数据互相隔离。
- Worker 中止、测试超时和候选变化均能停止执行并完成清理。
- 相同输入复用结果；源码、构建或计划变化使相关证据失效。
- Builder 异议只能触发有依据的复核，不能直接取消测试或授予 pass。
- 预检通过后，后续包制造的回归仍由模块边界或最终验收发现。

实现时运行相关单元、集成和真实 Chromium 测试，交付前执行项目要求的 `npm run test:all`。本文仅为文档，不宣称上述能力已通过验证。

### 第三步：比较实际收益

在相同需求、模型和总预算下，比较开启与关闭预检的运行。尽量使用多次配对运行，区分模型随机波动。统计官方得分、需求遗漏、边界修复次数、总耗时与 token、重复测试成本，以及人工抽查确认的 Planner 误报和漏报。

官方测试和结果仅用于运行后的离线评估，继续不进入 Builder、Planner 或运行时裁决。预检通过率提高不能代替官方得分或人工需求核验。

若预检主要增加等待、追逐错误定位器或挤占后续功能实现时间，应调整范围、轮次或暂缓启用，而不是单纯增加重试。是否推广、5 分钟起始上限是否合适、是否扩展到修复调用，均由这一步的证据决定。
