# ShallowCode 提分与效率改进路线

日期：2026-09-14  
代码基线：`8799348`（模块优先管线、网关 JSON 模式）  
状态：待实施建议。优先级表示验证和实施顺序，不代表已经测得的收益排序。

## 目标与证据基础

目标是在给定投入下提高交付应用的业务正确率，同时减少无效开发、验收失败和回滚损失。默认总预算保持不限时；固定时间对照实验通过显式参数设置预算。

已有证据与待验证假设应分开：

- 旧版 main 日志覆盖约108分钟，其中约101分钟处于 Builder 调用内；标签、删除、归档三个包合计约63分钟，最终回滚。删除与归档的退出原因涉及 Judge 无法建立有效证据。这些数据支持模块级开发与保留不确定候选的方向。
- 上述耗时来自重构前运行，不能直接用于判断当前版本的瓶颈，也不能推导 token 分布。当前入口仍将模型 usage 标为 `unavailable`。
- 当前 main 先实现完整模块，再独立验收。模块间仅检查构建、启动与候选一致性，功能反馈仍集中在首轮实现之后，存在回归累积风险。
- 当前第二轮集中修复会从更新后的 `results` 生成观测；第一轮没有独立验证的改善时，则回滚并停止。这是现有停止策略。
- `verified` 表示当前内部探针通过，`delivered` 表示全部内部需求通过且最终运行验证通过。它们不等于外部业务正确率。

本轮优先建立可比较的运行证据，然后改善修复反馈和模块间反馈，再根据真实失败样本调整覆盖与修复策略。

## 优先级总览

| 顺序 | 方向 | 主要目的 | 启动条件 |
| --- | --- | --- | --- |
| P0 | 当前版本对照与故障归因 | 找到实际瓶颈并建立可复查基线 | 立即开展 |
| P1 | 结构化、带依据的修复观测 | 降低修错方向和反复猜测的成本 | 与P0并行准备 |
| P2 | 模块间轻量独立检查 | 提前发现共享行为回归 | 明确检查范围和修复额度后 |
| P3 | 按需求检查行为覆盖 | 提高探针相关性与有效覆盖 | 根据P0收集的漏检样本 |
| P4 | 基于代码版本调整修复停止策略 | 利用有价值的失败尝试 | 有明确的过早停止样本后 |
| P5 | 输入与执行开销优化 | 降低已确认的重复成本 | 测量证明收益值得投入后 |

## P0 — 建立当前版本对照与故障归因

### 实施范围

保留 baseline 和当前 main 两条对照路径，固定模型、网关、需求、参考资源、机器资源及依赖版本。每次运行使用独立输出目录，记录代码提交、工作区差异及 prompt/schema 摘要。避免共享产物和服务端业务数据。

按以下层次记录：

| 层次 | 最小指标 |
| --- | --- |
| 实现 | 模块完成量、Builder调用耗时、调用次数、自测prepare次数、模块恢复次数 |
| 验收 | 规划/执行/定位恢复耗时；schema错误、定位失败、基础设施故障、可复现业务失败数量 |
| 修复 | 每轮输入失败、改善需求、回归需求、未完成复验需求、保留或恢复原因 |
| 交付 | 最终可运行状态、implemented/verified/failed/inconclusive/todo/blocked数量 |
| 外部结果 | 操作者在隔离评估流程中取得的业务正确率，以及与运行版本对应的结果记录 |

优先复用 ledger、候选事件及现有摘要。只有现有日志无法区分瓶颈时，才增加必要的 Builder 工具耗时或用量观测；无法取得的数据明确标记不可用。请求字符数或字节数只能作为输入规模指标，不能当作实际 token 消耗。

### 实验与判断

- 先取得当前 main 的完整运行基线，再做单因素改动。`data/github`、`data/sheet` 都纳入，额外题目使用相同记录方式。
- 使用显式预算进行15、30、45分钟档位的独立运行；这改变的是阶段额度，不能把它们视为同一次不限时运行的截面。
- 同时报告实际墙钟耗时。阶段预算不是进程硬截止，清理和最终验证可能产生额外时间。
- 每个配置尽量重复至少3次，报告中位数与范围；单次结果只作为探索性证据。
- 外部正确率和可运行率是主要结果，内部状态用于解释变化。一次提高内部 verified 率不能单独证明提分。

运行中的 Builder、Planner 和 Runner 均不访问官方测试或评分输出。外部结果由操作者用于离线比较，不回灌为运行时修复输入。

### 改动点与验证

检查 `index.ts`、`src/human-log.ts`、`src/types.ts` 与现有评估脚本的记录是否足够。新增事件同时验证脱敏、版本关联和中文日志；遵循 `docs/2026-09-07-observability-arc-projection.md`。

## P1 — 结构化、带依据的修复观测

### 现状

Runner 将 Playwright 异常压缩并截断为1000字符，再由 `toBuilderShadowObservation` 传递白名单消息。异常通常含 Expected/Received，但字段不稳定，可能被截断，也缺少明确的预期依据。

### 实施范围

在断言失败诊断中增加可选的结构化信息：

- 关联需求ID及可说明该行为的需求片段；无法直接引用时标明是根据需求推导。
- 断言所检查的行为、期望值和实际观测值；保留必要的匹配语义，例如包含匹配或允许的多个值。
- 观测对应的候选版本标识，由控制器在私有记录中绑定，不向 Builder 暴露内部 Git 状态。

期望值来自 Runner 执行的断言上下文，但不能仅凭这个来源就视为需求真值。缺少需求支持的预期应进入 Judge 复核，而不是自动驱动应用修改。实际值无法可靠取得时明确标记不可用；避免事后再次读取页面并将变化后的值冒充失败瞬间的观测。

Builder 只接收当前修复所需的行为差异与需求依据。所有新增文本经过现有脱敏和长度限制，完整计划、定位策略和候选定位列表留在 Judge 侧。

### 改动点、验证与风险

涉及 `src/types.ts`、`src/judge/playwright-probe-runner.ts`、`src/builder/shadow-observation.ts`、`src/builder/prompt-input.ts`、修复prompt及日志。

验证文本/值/数量断言、空值、包含匹配、多个允许值、实际值不可得、截断与凭证脱敏；检查新增观测不包含隐藏计划。用相同缺陷比较修复前后的独立验证结果和耗时。

主要风险是给错误预期增加权威感，或诊断采集失败覆盖原始业务失败。字段采集必须保持诊断性质。

## P2 — 模块间加入轻量独立检查

### 目的与范围

保持完整模块开发与实现会话复用，在模块边界增加少量独立功能反馈，缩短公共接口和数据模型回归的发现间隔。

- 首个模块建立一条基础业务路径。后续模块选择一条与其核心职责相关的新路径，并重跑少量已通过的关键依赖路径。
- 优先检查状态变更和重新读取，例如创建后列表出现、刷新后仍存在；单纯元素存在或健康检查不能替代业务路径。
- 复用合法计划，只有定位确实需要恢复时才调用模型。检查数量有明确上限，最终完整验收仍负责更广的覆盖。
- 每次检查绑定冻结候选，使用隔离业务数据。缓存的通过结果不能直接转移到新版本，缓存计划则可以重新执行。

### 失败处理

| 结果 | 处理 |
| --- | --- |
| 既有关键路径可复现回归 | 暂停新增模块，使用现有全局修复额度处理；无法修复则恢复当前模块之前的检查点 |
| 新模块关键依赖路径失败 | 先处理该失败，避免后续模块建立在已知不可用行为上 |
| 新模块非关键业务缺陷 | 记录并纳入集中修复队列 |
| Planner、定位或浏览器故障 | Judge侧有界恢复；保留实现并记不确定，不将检查缺失当作通过 |

增量检查的代码修复复用运行级额度，不增加每模块独立的多轮修复梯子。实施前明确关键路径选择、检查上限、额度消耗及最终集中修复的共享规则。

### 改动点、验证与风险

涉及 `src/pipeline.ts`、`src/judge/audit.ts`、调度上下文、状态与事件；需要调整当前“所有模块先实现再验收”的流程约定。

验证回归在下个模块前被发现、Judge故障不会误回滚、修复反馈对应当前代码、全局修复次数不被放大、旧版本证据不会授予新版本通过。

通过对照实验判断新增检查耗时是否被减少返工抵消。检查范围过大或定位噪声过高时，应收缩增量检查范围。

## P3 — 按需求行为检查覆盖

### 实施范围

从需求明确要求的可观察行为出发，建立轻量覆盖检查；case数量只用于控制规模。

- 持久化要求：检查是否有状态变更后的重新加载或新会话读取，以及相应结果断言。
- 输入校验要求：检查声明的非法操作是否被拒绝，以及需求支持的反馈或成功效果缺失。
- 权限要求：检查对应身份与被限制操作的结果。
- 种子数据：仅在相关列表、页面或身份下验证适用条目；产品级种子数据检查统一安排，避免每个原子需求重复执行。

一个case可以覆盖多个相关行为。关键词可用于提出待检查项，不能直接成为新增产品要求或强制增加case数的依据。对计划结构能可靠判断的遗漏先给出明确反馈；语义无法确定时保留不确定性，不把Planner覆盖不足直接记为应用失败。

### 改动点、验证与风险

涉及 Planner 输入/提示、`probe-schema.ts`、`audit.ts` 和候选数据初始化。验证一个case覆盖持久化、两个重复case仍缺少关键行为、种子数据与当前需求无关、权限限制下不应显示全部数据等样例。

主要风险是错误附加需求、重试增加以及无效覆盖检查。先从实际漏检样本中选择少量明确规则，并测量新增 inconclusive 与外部正确率变化。

## P4 — 根据版本一致性评估修复停止策略

### 现状与启动条件

当前保留第一轮修复后会执行 `results = next`，第二轮使用新报告。第一轮无改善时停止，是控制成本的策略；是否过早停止，需要失败样本支持。

重点区分：修复确实无效、出现回归、复验未完成，以及同一需求的失败数量减少但仍未整体通过。这些情况不应在离线分析中混为一类。

### 可评估的调整

在总修复轮次仍至多两轮的前提下，对“无回归但未完成整个需求”的样本评估是否值得第二次尝试。每次决策都必须保证代码与证据一致：

- 若保留候选继续修复，后续观测必须来自该候选，并单独保留可恢复检查点；尚未验证的改善不能冒充已接受结果。
- 若恢复原版本，第二次尝试的当前失败依据仍对应恢复后的代码。被丢弃尝试的信息只能作为明确标注的历史诊断，不能当作当前事实。

只有证明新策略能稳定改善结果且成本可接受后才实施。验证候选A→候选B→恢复A的报告关联、被拒绝版本的计划变化、第二轮实际输入以及回归保护。两轮是当前成本边界，不宣称已经证明它是最优轮数。

## P5 — 测量驱动的输入与执行优化

### 前置需求压缩

先统计传递依赖输入规模及其在请求中的占比。前置场景和准确UI字符串可能用于建立登录、创建数据等操作前提，应保留这些执行所需信息。

优先去除同次请求中的完全重复内容；跨请求裁剪或摘要须验证前提建立成功率。固定依赖深度截断并不能保证无损。

### 批量规划或执行

独立性来自 Judge 与 Builder 的信息隔离及判断职责。保留逐需求归因、完整覆盖和数据隔离时，可以评估批量规划或运行以减少启动与请求开销；先确认这些开销在当前版本中确实显著。

### 会话复用

继续在恢复代码后更新实现会话。若将来测得会话重建成本显著，再研究可靠的状态同步；仅有 git 无 diff 不能证明模型对文件和运行状态的记忆仍正确。

每项都用输入规模、实际耗时、故障率和外部正确率共同评价，不能预设为“只省token、不影响质量”。

## 实施与验收规则

1. P0建立当前版本基线，P1准备结构化诊断，分别验证后再实施P2。
2. P3、P4根据明确的漏检或停止样本选择性实施；P5在确认开销后进行。
3. 每项改动保持可单独回退；涉及管线行为同步状态、日志、README和AGENTS，交付前执行 `npm run test:all`。假模型测试证明控制器行为，真实模型实验验证耗时和效果。
4. 目标应用的业务代码由OpenCode唯一编写。Judge不读取应用源码、diff或Builder会话；Builder不读取隐藏探针计划、控制器私有台账及官方测试结果。
5. 默认不强制Builder建立传统测试套件或执行完整TDD；保留按需编写开发测试的能力，其结果不授予独立验收通过。
6. 阶段预算保持显式启用。所有收益描述都是待检验假设；真实运行结果应记录样本、配置及局限。
